# Самообновление помощника бездиска (ClubDisklessHelper 1.8.0) — спецификация

Дата: 2026-11-06, ред. 2 (после проверки: тихие сбои, способ выхода, подтверждение, очередь); ред. 2.1 (после проверки
жизненного цикла: простой сервера не считается молчанием ПК, поздний `confirmed` после `noReturn`). Статус: на
утверждении у владельца клуба.

## 1. Что нужно клубу

Обновлять помощник на ПК без человека у ПК. Сейчас каждое обновление — вход `Club` с Shift на каждом гибриде и строка
`update-helper-net.ps1`; на 22 гибридах это обход всего клуба.

Решения владельца (2026-11-06):

- Обновление запускается **кнопкой в панели** сервера клуба: для выбранных ПК или для всех гибридов; не автоматически.
- Помощник перезапускается на новую версию **между сеансами**: пока у игрока выданы сохранения, он ждёт конца сеанса.
- Способ замены — «А»: служба сама кладёт новый exe рядом, меняет файлы местами и завершается; Windows перезапускает
  службу уже новой версией. Новая версия, которая падает, сама возвращает прежнюю.
- Раскатка: не больше 3 ПК одновременно, очередь останавливается на первой ошибке.
- Бездиск: обычные места кнопку не получают (C: сбрасывается при загрузке); мастер эталона в сеансе мастера — получает
  (обновление попадает в эталон, дальше `seal-golden` и публикация).
- 1.8.0 ставится на ПК последний раз вручную; дальше — кнопкой.

Что значит «между сеансами» (ограничение v1): помощник знает о сеансе только по выданным сохранениям
(`profile.attach`). Сеанс гостя, сеанс без сохранений или с неудавшейся выдачей для него — «свободно», и перезапуск
может прийти посреди игры: игра и диски G:/H: не прерываются, на 5–30 с (при откате — до 2 минут) недоступен только
канал сохранений. Шелл повторяет подключение к каналу (п. 5.2).

Критерий готовности (PC-22 и PC-23, `HelperUpdates:MaxActive=1`):

- кнопка ставит пробную 1.8.1 без человека у ПК; панель показывает «проверка», затем «готово» и сборку 1.8.1; сессии
  iSCSI G:/H: до и после замены — те же;
- пробные сборки, которые ломаются тремя способами (падение после старта, ошибка внутри службы с аккуратной остановкой,
  зависание без отчёта), — каждая заканчивается откатом на прежнюю сборку или ошибкой `noReturn`; поручение — «ошибка»,
  поручение PC-23 — «на паузе».

## 2. Как это работает

```
панель ── «обновить ПК 11-20 до 1.8.1» ──► сервер: поручения в очереди (helper_updates)
                                             │  отчёт ПК раз в 30 с; не больше 3 активных
ПК ◄── ответ на отчёт: helperUpdate {id, версия, SHA256, размер, путь} ──┘
помощник: скачивает .new в фоне → SHA256 → ждёт свободного момента → отчёт «applying» → .old/.new местами
          → завершает свой процесс → Windows (действия при сбое) через 5–30 с запускает службу → новая версия
новая версия: «проверка» 10 минут (5 принятых отчётов, без падений) → «confirmed», .old стёрт → сервер: «готово»
падает 3 раза подряд → возвращает .old → прежняя версия сообщает «failed» → сервер: «ошибка», очередь на паузу
молчит 10 минут после «applying» → сервер: «ошибка» noReturn, очередь на паузу
```

Принцип API не меняется: сервер не управляет Windows, он сообщает желаемую сборку в ответе на отчёт (как назначение G:
и мастер-тома); когда её ставить, решает помощник и сообщает факты.

## 3. Сервер клуба (Club.Server)

### 3.1. Сборки

- Сборки лежат в `<Imaging:PxeRoot>/tools/ClubDisklessHelper-<X.Y.Z>.exe` (кладёт администратор, файлы root, сервер
  только читает; копировать под временным именем и переименовывать на место — файл моложе 60 с сервер не берёт).
  Имя — строго `^ClubDisklessHelper-\d+\.\d+\.\d+\.exe$`, версия — из имени.
- Сервер сам считает SHA256 и размер (кэш по размеру и времени изменения).
- Целью кнопки может быть только сборка **1.8.0 и новее** (умеет протокол подтверждения и отката). Старые файлы видны в
  списке с пометкой «только вручную»; поручение на них — отказ `targetTooOld`.
- В поручение записываются файл, версия, SHA256 и размер на момент запуска. Файл заменили (другой SHA256) или удалили —
  все незавершённые поручения по нему → `failed` (`buildChanged` / `buildMissing`), очередь на паузу. Проверяется при
  каждой выдаче поручения и в работнике очереди (п. 3.3).

### 3.2. Данные (миграция `M0013_HelperUpdates`, id `2026110601`)

- `machines.helper_build text NULL` — SHA256 exe из последнего отчёта G: или регистрации (строчные 64 hex). Пишется
  как есть, без «оставить прежнее»: отчёт без поля (помощник старше 1.8.0) обнуляет его.
- `helper_updates`: `id uuid`, `machine_id` (FK, каскад), `file`, `version`, `sha256`, `size bigint`,
  `state` (`queued`, `paused`, `active`, `done`, `failed`, `cancelled`), `progress` (последнее от помощника:
  `downloading`, `waiting`, `applying`, `confirming`), `reason` (почему ждёт: `session`, `command`, `master`), `error`,
  `message`, `requested_by`, `created_at`, `activated_at`, `progress_at`, `updated_at`, `finished_at`.
  Не больше одного незавершённого поручения на ПК (частичный уникальный индекс по `machine_id` для `queued`, `paused`,
  `active`).

### 3.3. Очередь

Все переходы — в одной транзакции под `pg_advisory_xact_lock` очереди: обработка отчёта ПК, работник очереди и
действия панели не пересекаются, и предел активных соблюдается строго.

Порядок обработки отчёта G: (`PUT …/status`, в той же транзакции, до ответа):

1. записать `helper_build`;
2. применить `helperUpdate` отчёта к поручению с тем же `id` в любом незавершённом состоянии: прогресс; `confirmed` →
   `done`; `failed` → `failed` (с ошибкой) и пауза, кроме `helperTooOld`; отчёт с `failed` по уже отменённому за сутки
   поручению — только запись ошибки; `confirmed` по поручению, завершённому за сутки с `noReturn`, — `done` (ошибка
   снята, строка в журнал), пауза остаётся до «Продолжить» (ред. 2.1); по другим ошибкам `confirmed` не меняет ничего;
3. помощник старше 1.8.0 у ПК с активным поручением → `failed`/`helperTooOld` без паузы;
4. повышение: поручение этого ПК в `queued` → `active`, если активных меньше `HelperUpdates:MaxActive` (по умолчанию 3),
   в очереди нет паузы, и ПК сейчас можно обновлять (ниже);
5. ответ: `helperUpdate` — только для `active` поручения этого ПК, если ПК всё ещё можно обновлять и сборка на месте.

Работник очереди (фоновая служба, раз в 30 с, под той же блокировкой):

- `active` с прогрессом пусто/`downloading`/`waiting`, ПК молчит 10 минут → `queued` (место освобождается);
- `active` с прогрессом `waiting` дольше 30 минут → `queued` (долгий сеанс не держит место; помощник стирает `.new`,
  позже скачает снова);
- `active` с прогрессом `applying` или `confirming`, и 10 минут от ПК нет `confirmed` и нет отчёта с прогрессом (ПК молчит
  или шлёт отчёты без поручения) → `failed`/`noReturn`, пауза;
- `active` без прогресса 10 минут, а ПК отчитывается → `failed`/`noProgress`, пауза;
- проверка файлов сборок (`buildChanged`, `buildMissing`).

Время, пока сервер был выключен, не считается (ред. 2.1): каждое правило по времени выше считает от более поздней из
двух отметок — своей (`last_seen_at`, `progress_at`, `updated_at`) и запуска работника. После простоя сервера ПК
получают полные 10 (30) минут, чтобы отчитаться.

Пауза: все `queued` → `paused`. Новый запуск во время паузы создаёт поручения сразу `paused`, ответ панели об этом
говорит. «Продолжить» — `paused` → `queued`. «Отменить» (всё или одно поручение) — `queued`, `paused`, `active` →
`cancelled`; сервер перестаёт присылать поручение, помощник бросает загрузку или ожидание и стирает `.new`. Если
помощник уже отправил `applying`, замена завершается (поручение остаётся `cancelled`, сборка ПК видна в панели).
Разные сборки для разных ПК в очереди одновременно допустимы; один запуск — одна сборка.

Кого можно обновлять (проверяется при запуске, при повышении и при каждой выдаче):

- ПК одобрен и `boot_mode = local`;
- или мастер эталона бездиска во время сеанса мастера: `diskless_image.master_machine_id` = этот ПК, у ПК диск
  `seat_disks.kind = 'master'`, и последняя загрузка по сети (`seat_disks.last_boot_at`) — после включения режима
  мастера. Сеанс мастера закрыли раньше, чем замена прошла, — `cancelled`/`diskless`.

Отказ при запуске — в порядке проверки: `unknown` (нет такого номера), `notApproved`, `diskless` (место бездиска —
«через эталон»), `helperTooOld` (помощник старше 1.8.0 — ставится вручную), `targetTooOld`, `busy` (уже есть
незавершённое поручение), `current` (у ПК уже эта сборка). Если отчёт ПК показывает целевую сборку (`helperBuild` =
SHA256), а поручение в `queued`, `paused` или `active` без прогресса `applying`/`confirming` (ПК обновили вручную), —
оно `done` без выдачи. Откат на более старую сборку (не ниже 1.8.0) — обычное
поручение.

Действие, ПК, сборка и итог — одной строкой в журнал сервера.

### 3.4. API для помощника (G:, `PUT /diskless/v1/machines/{id}/status`)

- В ответе `StatusAccepted` — необязательное `helperUpdate {id, version, sha256, size, path}`; без поручения поля нет
  (старые помощники и побайтовая проверка провода 1.5.1 — без изменений). `path` — относительный:
  `pxe/v1/files/tools/ClubDisklessHelper-1.8.1.exe`.
- В отчёте `MachineStatus` (1.8.0+) — необязательные `helperBuild` и
  `helperUpdate {id, state, reason, error, message}`. `state`: `downloading`, `waiting`, `applying`, `confirming`,
  `confirmed`, `failed`; `reason` (при `waiting`): `session`, `command`, `master`; `error`: `downloadFailed`,
  `hashMismatch`, `noRecovery`, `swapFailed`, `startFailed`, `noRollback`; `message` — текст до 500 символов.
- Все эти поля — обычные строки: незнакомое значение или `helperBuild` не из 64 hex пишется в журнал и пропускается,
  **отчёт никогда не получает 400** из-за них (иначе ПК «пропадает» из панели).
- Регистрация (`register`) тоже передаёт `helperBuild`.
- `docs/diskless-api.yaml` — новые поля и абзац про желаемую сборку.

### 3.5. Панель

- Экран ПК, карточка «Обновление помощника»:
  - сборки из `tools`: версия, размер, начало SHA256; старше 1.8.0 — «только вручную»;
  - выбрать сборку, ПК — номера (`22`, `11-20, 25`, как у зон) или «все гибриды» → «Запустить»; ответ — сколько
    поставлено в очередь (или на паузу) и кому отказано с причиной;
  - очередь: активные, в очереди, на паузе, готово, ошибки за сутки; «Продолжить», «Отменить», отмена одного ПК.
- Столбец «Помощник»: версия, начало SHA256 сборки и состояние поручения: «в очереди», «на паузе», «назначено» (активно,
  отчёта ещё нет), «скачивает», «ждёт: сеанс / команда шелла / правка библиотеки», «перезапуск», «проверка», «готово»,
  «отменено», «ошибка: <код и текст>»; «вручную (старше 1.8.0)»; у мест бездиска — «через эталон».
- В `MachineView` — `helperBuild`, `helperUpdate` и вычисленное сервером `helperUpdatable` с причиной, если нельзя
  (панель не выводит это из `bootMode` сама).
- API: `GET /panel/api/v1/helper/builds`, `GET/POST /panel/api/v1/helper/updates`,
  `POST /panel/api/v1/helper/updates/resume`, `POST /panel/api/v1/helper/updates/cancel`,
  `POST /panel/api/v1/helper/updates/{id}/cancel`.
- Тексты — ru, uz (латиница), en.

## 4. Помощник на ПК (Club.Helper 1.8.0)

### 4.1. Каркас процесса (обязателен для всех сборок с 1.8.0)

- **Страж обновления — первым в `Main`**, до сборки хоста, только файлы и JSON из BCL, в своём `try`, журнал — прямо
  `EventLog.WriteEntry("ClubDisklessHelper", …)`. Он читает `update.json` и решает: счётчик попыток, откат (п. 4.4).
- **Любой ненормальный конец хоста — завершение процесса**, которое Windows считает сбоем (без `SERVICE_STOPPED`):
  исключение в фоновой службе, ошибка при старте, хост остановился не по команде Windows. Остановку по команде Windows
  отмечает свой наследник `WindowsServiceLifetime` (OnStop/OnShutdown), он же пишет «чистый выход» в `update.json`;
  в остальных случаях помощник пишет текст ошибки в `update.json` и завершает себя
  (`Process.GetCurrentProcess().Kill()`). По умолчанию в .NET 10 исключение в фоновой службе останавливает хост
  аккуратно, и Windows **не** перезапускает службу — этого быть не должно.
- При старте — SHA256 своего exe (`helperBuild`) и проверка действий Windows при сбое службы: нет или другие — ставит
  `restart/5000/restart/5000/restart/30000`, сброс счётчика — сутки.
- Exe и служба те же: `%ProgramFiles%\ClubDiskless\ClubDisklessHelper.exe`, служба `ClubDisklessHelper`, ImagePath не
  меняется.

### 4.2. Поручение и загрузка

- Поручение из ответа на отчёт G: принимается, если `path` строго `pxe/v1/files/tools/ClubDisklessHelper-X.Y.Z.exe`,
  SHA256 — 64 hex, размер — до 300 МБ. Своя сборка — ничего не делать (сервер закроет поручение по `helperBuild`).
- Поручение, по которому уже была ошибка на этом ПК, не выполняется снова: список `{id, sha256, error}` хранится в
  `%ProgramData%\ClubDiskless\update-failed.json` (переживает перезапуски и откат; последние 20);
  по такому поручению помощник шлёт `failed` в каждом отчёте. Новое поручение
  (другой `id`) выполняется.
- Принятый ответ без `helperUpdate` или с другим `id` — отмена: бросить загрузку или ожидание, стереть `.new`. Ответа нет
  (сервер недоступен) — не отмена.
- Скачивание — в фоне, не в такте (отчёты не прерываются), клиентом для больших файлов, по адресу сервера из
  `helper.json` (HTTPS, сертификат клуба), в `%ProgramFiles%\ClubDiskless\ClubDisklessHelper.exe.new` (права папки, тот
  же диск), не больше `size` байт, SHA256 по ходу, в конце — сброс на диск (`Flush(true)`). Не совпал — `.new` стёрт,
  `hashMismatch`.

### 4.3. Замена

Только в цикле `HelperService`, сразу после такта (`loops.TickAsync`) и после конца такта сохранений:

1. Готовность: `.new` скачан и проверен; последний принятый ответ несёт то же поручение (`id`, SHA256); действия при
   сбое службы на месте (иначе `failed`/`noRecovery`, без замены); помощник свободен — без ожидания взят замок
   `SavesService` (нет выдачи, не идёт команда канала), нет выданных сохранений, ни в одном цикле (G:, H:) нет
   назначения мастер-тома и состояние мастер-тома — нет или `none`. Не свободен — `waiting` с причиной
   (`session`, `command`, `master`).
2. Свободен и готов — прогресс `applying`; он уходит **обычным полным отчётом** следующего такта. Отчёт не принят —
   замены нет, попытка в следующем такте.
3. После такта, где `applying` принят: снова пункт 1 (замок `SavesService` держится до конца), SHA256 `.new` ещё раз,
   открыть `.new` монопольно (антивирус дочитал; повтор до 60 с); `update.json` (через `.tmp`, сброс на диск, перенос)
   `{v:1, id, fromSha, toSha, toVersion, phase: "prepared", attempts: 0}`; переименования подряд:
   `ClubDisklessHelper.exe` → `.old`, `.new` → `ClubDisklessHelper.exe`. Ошибка — имена обратно, `swapFailed`, замок
   отпущен; вернуть имена не удалось — служба не завершается, повторяет, `swapFailed` с текстом `restoreFailed`.
4. `phase: "swapped"` в `update.json` (со сбросом), дождаться, пока не идёт обновление токена (замок продления в
   `DisklessApiClient`, держать до конца), и завершить свой процесс (`Kill`). Windows через 5–30 с запускает службу.
- Пока замок `SavesService` взят обновлением, канал отвечает: `ping` — `ok` и `updating: true`; `profile.attach` и
  `profile.detach` — ошибка `updating` (повторить позже).
- Два процесса помощника одновременно не работают: Windows запускает службу, когда старый процесс завершился.

### 4.4. Подтверждение и откат

Страж в `Main` (п. 4.1) по `update.json`:

- **своя сборка = `toSha`, фаза `swapped`**: если прошлый запуск этой сборки не оставил «чистый выход» — попытка +1
  (обычная перезагрузка ПК и сервер недоступен — не попытки). Попыток больше 3 → откат: `.old` есть и его SHA256 =
  `fromSha` → `ClubDisklessHelper.exe` → `.failed`, `.old` → `ClubDisklessHelper.exe` (с тем же возвратом имён при
  ошибке), фаза `rolledBack`, ошибка `startFailed` с текстом последнего исключения; `.old` нет или не тот — ничего не
  трогать, ошибка `noRollback`, работать дальше. Ветка отката запускает минимальный хост службы и, когда Windows
  считает службу запущенной, завершает процесс (`Kill`) — чтобы Windows точно запустила прежнюю сборку.
- **своя сборка = `toSha`, работает**: прогресс `confirming` («проверка»). Подтверждение — 10 минут работы, не меньше 5
  принятых отчётов G: и ни одного падения: стереть `.old`, `.failed` и `update.json`, в отчёт — `confirmed`. Сервер ставит «готово» только по `confirmed`.
- **своя сборка = `fromSha`**: фаза `prepared` — замена прервалась: стереть `.new` молча, ошибки нет (поручение
  продолжится); фаза `rolledBack` или есть ошибка — `failed` с ошибкой и текстом в каждом отчёте, пока принятый ответ не
  перестанет нести это поручение; затем удалить `update.json` (поручение уже в `update-failed.json`).
- **сборка ни та ни другая** (поставили вручную): `update.json`, `.new`, `.old`, `.failed` удаляются.
- **`update.json` не читается**: `.old` не удалять, пока сборка не подтверждена; восстановить `fromSha` по SHA256
  `.old`.
- Хвосты при старте без `update.json`: `.new`, `.failed` удаляются; `.old` — тоже.

### 4.5. Прочее

- `ping` канала отвечает и сборкой (`build`).
- Журнал «Приложение»: одна строка на каждый шаг (поручение, скачано, ждёт, замена, проверка, подтверждено, откат) с
  версиями и SHA256; строки стража — напрямую в журнал событий.

## 5. Скрипты и шелл

### 5.1. Наши скрипты (`scripts/`)

- `scripts/shell/shell-preflight.ps1`, `shell-install.ps1`, `shell-uninstall.ps1`: вместо списка SHA256 — exe службы
  `ClubDisklessHelper` в `%ProgramFiles%\ClubDiskless`, версия файла (числами, `FileMajorPart/MinorPart/BuildPart`)
  не ниже 1.6.0. `shell-install`: «после» — служба работает и версия не ниже «до». `shell-uninstall`: возврат копии exe
  — только если exe пропал, и после выхода процесса.
- `install-helper.ps1`, `update-helper-net.ps1` — ставят 1.8.0 (закреплённый SHA256), удаляют хвосты самообновления,
  `update.json` и `update-failed.json`.
- `seal-golden.ps1`, `seal-hybrid.ps1`: если есть `update.json`, `.new` или `.failed` — FAIL «обновление не
  подтверждено: дождаться “готово” или поставить вручную», а не удаление; `.old` — удалить, если `update.json` нет;
  `update-failed.json` — удалить;
  показать версию и SHA256 exe; после остановки службы проверить, что она не запустилась снова.

### 5.2. Шелл (`club-contracts/docs/SHELL_CHANGES.md`, п. 23 — дополнить)

- Канал недоступен (нет имени канала, нет соединения) — повторять подключение в пределах бюджета выдачи (60 с), а не
  сдаваться через 5 с; PID службы проверять при каждом подключении.
- Ответ `updating` на `profile.attach`/`profile.detach` — повторить через 5 с в пределах того же бюджета.

## 6. Ошибки и крайние случаи

| Случай | Что происходит |
|---|---|
| Хэш не совпал, загрузка оборвалась | `.new` стёрт, `hashMismatch`/`downloadFailed`, очередь на паузе |
| Нет действий Windows при сбое службы | замены нет, `noRecovery`, очередь на паузе |
| Антивирус держит файл | `.new` открывается монопольно до 60 с до первого переименования; не вышло — `swapFailed` |
| Новая версия падает при старте | после 3 падений — прежняя, `startFailed`, очередь на паузе |
| Ошибка внутри службы (аккуратная остановка хоста) | процесс завершается как при сбое, дальше — как падение |
| Новая версия падает после первых отчётов | `.old` хранится до подтверждения (10 минут), падения считаются, откат |
| Новая версия зависла или не может отчитаться | через 10 минут после `applying` — `noReturn`, очередь на паузе; ПК — вручную |
| Сервер недоступен во время проверки | перезапуски без падений — не попытки; подтверждение, когда сервер вернётся; сроки работника — от его запуска, `noReturn` за время простоя нет; `confirmed` после `noReturn` (за сутки) — «готово», пауза остаётся (ред. 2.1) |
| Питание пропало между двумя переименованиями | окно — доли секунды (файл заранее проверен и открыт); случилось — служба не стартует, ПК вручную |
| ПК выключили во время скачивания | через 10 минут поручение — снова в очереди; `.new` стирается при старте |
| Сеанс игрока длится часами | `waiting`; через 30 минут место отдаётся другому ПК, этот — снова в очереди |
| Отменили во время ожидания | помощник стирает `.new`, замены нет |
| Файл сборки в `tools` заменили или удалили | все незавершённые поручения по нему — `buildChanged`/`buildMissing`, пауза |
| Гибрид перезалили (h1e с 1.6.0) | `helperTooOld`; ставится вручную `update-helper-net.ps1` |
| Мастер эталона загрузился местом | поручение — `cancelled`/`diskless` |
| Место бездиска | кнопки нет: «через эталон» |
