# Сохранения игр игрока на сервере клуба — спецификация

Дата: 2026-11-05. Статус: на утверждении у владельца клуба.
Заменяет раздел 7 «Профили игроков» в `docs/diskless-full.md` (вход в лаунчеры в v1 не входит, см. «Не входит в v1»).

## 1. Что нужно клубу

Сохранения и настройки игр следуют за аккаунтом игрока. Игрок поиграл на ПК-5, закончил сеанс; потом вошёл на ПК-30,
запустил ту же игру — его прогресс на месте.

Решения владельца (2026-11-05):

- Папки для сохранения задаются в панели сервера клуба: путь в профиле Windows (`%LOCALAPPDATA%\GameName\Saved`) или
  в папке игры на G:/H: (`H:\Игра\Saves`). Список общий для всех игр и игроков.
- Один общий диск на всех игроков (около 600 аккаунтов). У каждого игрока — своя папка с его ID из кассы; место не
  резервируется, занимают только реальные файлы. Лимит — 200 МБ на игрока.
- Копирование только в конце сеанса. Шелл ждёт, пока сохранение закончится, и только потом выходит из Windows и
  стирает профиль. При входе шелл ждёт, пока сохранения разложены, и только потом даёт запускать игры.
- Изменения в шелле не обходим: что нужно от шелла — пишем прямо в `club-contracts/docs/SHELL_CHANGES.md` (п. 23).
- Папки на G:/H: разрешены. В начале сеанса такая папка возвращается к исходному содержимому опубликованной версии,
  поверх — файлы игрока; чужие сохранения и ник следующий игрок не видит.
- Гостям ничего не сохраняется.

Критерий готовности: на одном гибриде и одном бездисковом ПК тестовая команда «выдать / сохранить» (до готовности
шелла) переносит файлы игрока между ПК, папки на G:/H: очищаются для игрока без сохранений, сохранение больше лимита
отклоняется без потери прошлой версии; после п. 23 в шелле — то же через настоящий вход и конец сеанса.

## 2. Как это работает

```
Шелл (вход игрока)   ─ profile.attach {playerId, windowsUserSid} ─►  помощник на ПК (\\.\pipe\club-diskless-helper)
                                                                     ─► сервер клуба: «игрок X на ПК M», архив его папки
                                                                     ◄─ помощник раскладывает файлы ─► {ok:true}
Шелл (конец сеанса: игры закрыты) ─ profile.detach {playerId} ─►  помощник собирает файлы ─► сервер: новая версия
                                                                     ◄─ сервер подтвердил ─► {ok:true} ─► шелл выходит
                                                                        из Windows и стирает профиль
```

1. **Вход.** Шелл передаёт ID игрока (ID аккаунта в кассе) и SID пользователя Windows. Помощник:
   - находит профиль пользователя по SID (`HKLM\...\ProfileList\<SID>\ProfileImagePath`, не `C:\Users\player`
     напрямую — после неудачного удаления профиль бывает `player.<ПК>`);
   - получает с сервера список папок и архив папки игрока (сервер запоминает «игрок X на ПК M»);
   - для каждой включённой папки из списка: удаляет содержимое; для папки на G:/H: — возвращает исходное содержимое
     (п. 4.4); раскладывает файлы игрока из архива;
   - отвечает шеллу `{ok:true}`. Только после этого шелл даёт запускать игры.
2. **Конец сеанса.** Шелл закрывает игры и ждёт их завершения, затем передаёт ID игрока. Помощник собирает файлы
   из включённых папок (без исключений, п. 3.3) в архив и отправляет на сервер. Сервер проверяет лимит и целиком
   заменяет папку игрока новой версией (п. 3.4), прошлая становится предыдущей копией. Помощник отвечает шеллу
   `{ok:true}` только после подтверждения сервера; только после этого шелл выходит из Windows и стирает профиль.
3. **Защита хороших сохранений.** Сохранение принимается только с того ПК, которому сервер выдал сохранения этого
   игрока, и только если выдача на ПК закончилась успешно. Если выдача не удалась (сервер недоступен и т. п.),
   игрок играет без сохранений, а в конце сеанса ничего не отправляется — пустые папки не затирают прошлую версию.

## 3. Сервер клуба (Club.Server)

### 3.1. Общий диск

- Новый zvol `games/club/saves`, 250 ГиБ, sparse (пул games, свободно ~900 ГиБ на 2026-11-05). Подключается к ВМ по
  iSCSI так же, как диск образов `games/club/images`, файловая система ext4, точка монтирования `/srv/club/saves`,
  владелец — пользователь службы сервера.
- Структура:
  - `/srv/club/saves/<playerId>/<entryId>/…` — текущие файлы игрока по папкам из списка (`entryId` — ID записи
    списка, п. 3.2);
  - `/srv/club/saves/<playerId>.prev/…` — предыдущая копия;
  - `/srv/club/saves/.tmp/` — временные папки приёма.
- `playerId` — непрозрачная строка от шелла; сервер принимает только `[A-Za-z0-9-]{1,64}` (ID аккаунта в кассе —
  GUID). Кто такой игрок, сервер клуба не знает; в панели показывается ID.
- Бэкап: ночной снимок zvol и репликация в пул backup (свободно ~145 ГиБ на 2026-11-05) — отдельная задача
  репликации TrueNAS, как для остальных дисков. Если реальный объём сохранений превысит ~100 ГБ, пул backup
  расширить.
- Настройки сервера (env): `Saves__Enabled` (по умолчанию `false`), `Saves__Root` (`/srv/club/saves`). Если корень не
  смонтирован (нет файла-метки `/srv/club/saves/.club-saves`), API сохранений отвечает 503 и пишет предупреждение в
  журнал — запись на системный диск ВМ исключена.

### 3.2. Данные (миграция `M0012_PlayerSaves`)

- `save_settings` (одна строка): `limit_mb` (200), `excludes` (`text[]`, по умолчанию `{Logs, Crashes, CrashDumps,
  *.dmp}`).
- `save_entries`: `id` (uuid), `name`, `path` (шаблон, п. 4.2), `enabled`, `created_at`. Порядок — по `name`.
- `player_saves`: `player_id` (PK), `size_bytes`, `file_count`, `saved_at`, `machine_id` (откуда последняя версия),
  `last_result` (`ok`, `overLimit`, `rejected`, `error`), `last_result_at`, `last_error`.
- `save_leases`: `player_id` (PK), `machine_id`, `attached_at` — «игрок X на ПК M».

### 3.3. API для помощника (JWT машины, как остальной `/diskless/v1/machines/{id}/…`)

- `GET /diskless/v1/machines/{id}/saves/config` → `{enabled, limitMb, excludes[], entries:[{id, path}]}` (только
  включённые). Помощник читает при старте и раз в 5 минут — для исходного содержимого папок на G:/H: (п. 4.4).
- `POST /diskless/v1/machines/{id}/saves/{playerId}/attach` → записывает `save_leases(playerId → машина)`, забирая
  его у другой машины, если был (тот ПК пропал, не сохранив; касса не даёт открыть два сеанса одного игрока).
  Ответ: `200` с zip-архивом текущей папки игрока (записи `<entryId>/<относительный путь>`) и заголовком
  `X-Club-Saves-Config` (то же, что `saves/config`), или `204` с тем же заголовком, если у игрока ничего нет. Если
  текущей папки нет, а `.prev` есть (сбой между двумя переименованиями, п. 3.4) — отдаётся `.prev`.
- `PUT /diskless/v1/machines/{id}/saves/{playerId}` (тело — zip) → принимается, только если `save_leases` указывает
  на эту машину; иначе `409 notAttached` (`last_result = rejected`). Затем п. 3.4. Ответ `204`; ошибки: `413
  overLimit`, `400 badArchive`, `503 savesUnavailable`. Аренда снимается при успехе и при `overLimit`.
- `DELETE /diskless/v1/machines/{id}/saves/{playerId}/lease` → снять аренду без сохранения (помощник: выдача на ПК не
  удалась после ответа сервера).
- Тело PUT не больше `limitMb` + 10 % (лимит Kestrel поднят только для этого маршрута).

### 3.4. Приём сохранения

1. Поток пишется в `/srv/club/saves/.tmp/<uuid>.zip`; при превышении размера тела — `413` сразу.
2. Проверка и распаковка в `.tmp/<uuid>/`: только записи вида `<entryId>/<путь>` с `entryId` из списка; запрещены
   абсолютные пути, `..`, имена устройств Windows, двоеточия; сумма распакованных размеров ≤ `limitMb`, не больше
   50 000 файлов. Нарушение — `400 badArchive` или `413 overLimit`, временные файлы удаляются.
3. Замена: удалить `<playerId>.prev`, переименовать `<playerId>` → `<playerId>.prev`, переименовать `.tmp/<uuid>` →
   `<playerId>` (один раздел ext4, переименования атомарны). Обновить `player_saves`, снять аренду.
4. Блокировка на игрока (advisory lock PostgreSQL по `playerId`) на время attach, PUT и удаления из панели.
5. При старте сервера — очистка `.tmp/`.

### 3.5. Панель: вкладка «Сохранения»

- Карточка «Настройки»: лимит МБ, исключения (по одному в строке).
- Карточка «Папки»: таблица `название, путь, вкл/выкл, удалить`, кнопка «Добавить». Путь проверяется при сохранении
  (п. 4.2); подсказка — примеры путей.
- Карточка «Игроки»: `ID, размер, файлов, дата сохранения, ПК, последний результат`, поиск по ID, кнопка «Удалить»
  (удаляет папку, `.prev`, аренду и строку; с подтверждением).
- API панели: `GET/PUT /panel/api/v1/saves/settings`, `GET/POST /panel/api/v1/saves/entries`,
  `PUT/DELETE /panel/api/v1/saves/entries/{id}`, `GET /panel/api/v1/saves/players?query=&page=`,
  `DELETE /panel/api/v1/saves/players/{playerId}`. Тексты — ru/uz/en (`i18n.js`). Описание — в `docs/panel-api.md`.

## 4. Помощник на ПК (Club.Helper 1.7.0)

### 4.1. Канал для шелла

- Именованный канал `\\.\pipe\club-diskless-helper`, доступ только `SYSTEM` и `BUILTIN\Administrators` (агент шелла —
  служба LocalSystem). Одна строка JSON (UTF-8, `\n`) на запрос и одна на ответ; команды выполняются по одной.
- `{"op":"profile.attach","playerId":"…","windowsUserSid":"S-1-5-…"}`
- `{"op":"profile.detach","playerId":"…"}`
- `{"op":"ping"}` → `{"ok":true,"version":"1.7.0"}`
- Ответ: `{"ok":true}` или `{"ok":false,"error":"<код>","message":"<текст для журнала>"}`. Коды: `disabled`
  (сохранения выключены на сервере), `serverUnavailable`, `overLimit`, `notAttached`, `masterMode`, `profileNotFound`,
  `badRequest`, `internal`.
- Неизвестные поля игнорируются (например, `rememberLaunchers` из старого текста п. 23).

### 4.2. Шаблоны путей

- Профиль Windows: `%USERPROFILE%`, `%APPDATA%` (= `<профиль>\AppData\Roaming`), `%LOCALAPPDATA%`
  (= `<профиль>\AppData\Local`), `%LOCALAPPDATA_LOW%` (= `<профиль>\AppData\LocalLow`), `%DOCUMENTS%`
  (= `<профиль>\Documents`), `%SAVEDGAMES%` (= `<профиль>\Saved Games`). Профиль — по SID из `profile.attach`.
  Перенаправление папок на наших ПК выключено (`shell-install.ps1`, `folderRedirect.enabled = false`), поэтому
  «Документы» и «Сохранённые игры» лежат в профиле.
- Папка игры: абсолютный путь на букве библиотеки (`G:\…`, `H:\…`; буквы — из настроек библиотек сервера).
- Запрещено: другие диски, `..`, переменные кроме перечисленных, путь, равный корню профиля или корню диска.
  Проверка — и в панели (при сохранении записи), и в помощнике.

### 4.3. Выдача и сохранение

- **attach:** проверить, что ни одна библиотека на ПК не в режиме мастера (иначе `masterMode`); получить архив
  (отдельный HttpClient, тайм-аут 120 с); для каждой включённой записи — очистить папку, для G:/H: вернуть
  исходное содержимое, распаковать файлы игрока (те же проверки архива, что на сервере). Запомнить в памяти
  «выдано игроку X». При ошибке после ответа сервера — `DELETE …/lease` и ошибка шеллу.
- **detach:** только если в памяти «выдано игроку X» (иначе `notAttached`, ничего не отправляется); собрать файлы
  включённых записей, кроме исключений; если сумма больше лимита — `DELETE …/lease` и `overLimit` без отправки
  (сервер всё равно проверяет); отправить; забыть «выдано».
- Файлы, занятые другим процессом при сборке, — повтор 3 раза через 1 с, затем `internal` (шелл должен закрыть игры
  до `detach`).
- Права на разложенные файлы — наследуются от папки (профиль игрока, папка игры на G:/H:).

### 4.4. Исходное содержимое папок на G:/H:

- После подключения личного слоя библиотеки при загрузке ПК (до первого игрока) помощник снимает копию каждой
  включённой папки этой библиотеки в `%ProgramData%\ClubDiskless\saves-baseline\<entryId>.zip` (папка помощника,
  доступ только SYSTEM и администраторам). Если запись добавили в панели позже — копия снимается при получении нового списка,
  когда никому не выдано.
- Копия больше лимита — запись пропускается на этом ПК с предупреждением в журнале и статусе.
- На бездисковых ПК C: чистый после каждой загрузки, слой G:/H: тоже — копия всегда от опубликованной версии.

### 4.5. Прочее

- Сохранения выключены на сервере (`enabled = false`) — `disabled` на любую команду, кроме `ping`.
- Журнал: каждая команда (ID игрока, размер, время, результат) — в журнал событий, как остальной журнал помощника.
- Код Windows (канал, файлы, профиль по SID) — за интерфейсом в `Club.Helper.Core`, с подделкой для тестов, как
  `IWindowsStorage`.

## 5. Шелл (`club-contracts/docs/SHELL_CHANGES.md`, п. 23 — переписать, P0)

- При входе игрока (не гостя), **до** того, как разрешить запуск игр: `profile.attach` и ждать ответа до 60 с.
  Пока ждём — «Загружаем ваши сохранения…». При ошибке или тайм-ауте — пускать играть, показать «Сохранения
  недоступны».
- В конце сеанса (любая причина): закрыть игры, **дождаться их завершения**, затем `profile.detach` и ждать ответа до
  120 с; только после этого — выход из Windows и сброс профиля (`ProfileResetService`). При `overLimit` — показать
  игроку «Сохранения больше 200 МБ, не сохранены».
- Гостям — не вызывать.
- Встроенный `PlayerSettingsSync` шелла не должен работать с теми же папками (п. 84).

## 6. Ошибки и крайние случаи

| Случай | Что происходит |
|---|---|
| Сервер недоступен при входе | `serverUnavailable`, игрок играет без сохранений; в конце сеанса — `notAttached`, на сервере остаётся прошлая версия |
| Сохранение больше 200 МБ | `overLimit`, прошлая версия остаётся, в панели отметка у игрока |
| ПК выключили посреди сеанса | прогресс сеанса теряется (копирование только в конце); на другом ПК — последняя сохранённая версия, аренда переходит |
| Опоздавшее сохранение со старого ПК | `409 notAttached`, отметка `rejected` |
| Игрок на мастер-ПК | `masterMode`, ничего не выдаётся и не сохраняется |
| Диск сохранений не смонтирован на ВМ | `503`, на системный диск ВМ ничего не пишется |
| Сбой сервера между переименованиями | при выдаче берётся `.prev` |

## 8. Выкатка (каждый шаг — после ОК владельца)

1. Создать zvol `games/club/saves`, подключить к ВМ, ext4, метка `.club-saves`, задача репликации.
2. Обновить сервер клуба (миграция, `Saves__Enabled=true`), в панели — список папок.
3. Помощник 1.7.0: гибриды — `update-helper-net.ps1`; бездиск — эталон в режиме мастера, `install-helper.ps1`,
   `seal-golden.ps1`, публикация.
4. В клубе работает после п. 23 в шелле.

## 9. Не входит в v1

Вход в Steam и другие лаунчеры; ключи реестра (п. 82); сохранение посреди сеанса; привязка папок к конкретной игре;
шифрование архивов на сервере; автоудаление старых сохранений; имена игроков в панели (сервер знает только ID).
