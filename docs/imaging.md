# Образы Windows и перезаливка по PXE

Один `install.wim` из золотого образа — для сетевой заливки (WinPE по PXE + DISM). Перезаливка только ручная, из
панели. Хранятся две версии образа: текущая и откатная. PXE используется **только** для перезаливки: каждый день ПК
грузятся со своего диска, упавший PXE-сервер клуб не останавливает.

## Как это работает

```
Панель «Перезалить» ─► задание (reimage_jobs, pxe_armed) ─► класс club-reimage в резервации Kea
ПК перезагружается ─► прошивка UEFI: DHCP ─► Kea: ipxe-shim.efi (TFTP)   ← только машине с флагом
                    ─► shim (подписан Microsoft) ─► ipxe.efi (подписан iPXE)
                    ─► iPXE: DHCP ─► Kea: http://сервер/pxe/v1/boot.ipxe
                    ─► /pxe/v1/machines/<MAC>/boot.ipxe ─► wimboot (подписан Microsoft) + WinPE (boot.wim)
                       + club-deploy.ps1, winpeshl.ini, clubdeploy.json (подкладывает wimboot)
WinPE ─► POST /deploy/v1/start (MAC, диски) ─► план сервера: какой диск, какой образ, имя ПК
      ─► разметка ─► скачивание WIM на временный раздел (докачка) ─► sha256 ─► dism /Apply-Image
      ─► unattend (имя ПК поверх unattend от sysprep) + image.json ─► bcdboot
      ─► POST complete: сервер снимает флаг и убирает класс из Kea ─► только теперь перезагрузка
Windows ─► помощник сообщает imageVersion ─► задание «перезалит»
```

Остальные ПК получают от Kea адрес без имени загрузочного файла — прошивка сразу переходит к диску.

### PXE-флаг и главная гарантия

Флаг — класс `club-reimage` в резервации машины в Kea (`hosts.dhcp4_client_classes`). Сервер снимает его **только
после успешного bcdboot**, и WinPE перезагружается, только когда сервер подтвердил, что Kea уже не отдаст
загрузчик. Сбой на любом шаге → машина остаётся в PXE и при следующей перезагрузке снова попадает в WinPE,
попытка начинается с нуля. «Застряла в PXE» — безопасное состояние; мёртвого загрузчика получиться не может.

Отменить перезаливку можно, только пока WinPE не тронул диск (`diskTouched`). Потом — только довести до конца
или запустить заново (например, откатной версией): новое задание вытесняет упавшее и наследует `diskTouched`,
так что флаг и после этого не снять отменой.

### Secure Boot

Вся цепочка подписана (подробно и с проверкой подписей — `docs/research/secure-boot-pxe.md`): shim iPXE — Microsoft
UEFI CA 2011, `ipxe.efi` — iPXE Secure Boot CA (ему доверяет shim), wimboot — Microsoft (CA 2011 и 2023), WinPE —
Microsoft. Работает и с выключенным Secure Boot. `ipxe.efi` из пакета Ubuntu **не подписан** — его не ставить.

Помощник сообщает о Secure Boot на ПК (включён; есть ли в db сторонний CA 2011 и CA 2023; отозван ли в dbx PCA
2011). Сервер отказывает заранее, если загрузка всё равно не пройдёт, с понятной причиной в панели:

| Причина | Что сделать |
|---|---|
| `bootFilesMissing` | Установить файлы (ниже) |
| `secureBootThirdPartyCa` | В настройках платы включить «Microsoft 3rd-party UEFI CA» (или выключить Secure Boot на время перезаливки) |
| `bootFilesNotSigned` | Файлы на сервере без нужной подписи — поставить скриптом |
| `needsCa2023BootManager` | ПК отозвал старый загрузчик Windows — положить `boot/bootx64.efi` с подписью Windows UEFI CA 2023 |

ПК с отозванным PCA 2011 автоматически получают загрузчик CA 2023; остальные — загрузчик из boot.wim.

Почему класс, а не имя файла в резервации: проверено на настоящей Kea 3.0.3 — имя файла из резервации
перекрывает классы, и iPXE получал бы `ipxe.efi` снова, по кругу. Классы из резервации видят только
«дополнительные» классы (`only-in-additional-list` + `evaluate-additional-classes` в подсети) — так и сделано.

### Какой диск стирается

План даёт сервер (`TargetDisk.Choose`), WinPE перед стиранием сверяет номер, серийный номер и размер.

- Только внутренние шины: NVMe, SATA, SAS, RAID, ATA, SCSI. USB, iSCSI, SD, виртуальные — никогда.
- Помощник сообщает системный диск (с которого грузится Windows). Если он известен — стирается только диск с
  этим серийным номером. Нет такого диска (заменили SSD) — отказ, пока администратор не запустит перезаливку
  с «разрешить новый диск».
- Если системный диск неизвестен — только единственный подходящий по размеру. Несколько — отказ.
- Размер: EFI + MSR + распакованный образ с запасом 15 % + сам WIM (временный раздел) + 4 ГиБ, не меньше 64 ГиБ.

Разметка (только UEFI/GPT): EFI 260 МБ FAT32, MSR 16 МБ, Windows NTFS, временный раздел под WIM в конце диска.
После применения временный раздел удаляется, Windows расширяется на весь диск. Раздел восстановления (WinRE)
не создаётся. BIOS/Legacy — отказ `biosNotSupported`.

### Личность машины

Образ одинаков для всех. При заливке WinPE получает от сервера имя компьютера (из имени места, NetBIOS до 15
символов) и дописывает его в `Windows\Panther\unattend.xml` (проход specialize) поверх unattend, который положил
sysprep: настройки OOBE золотого образа сохраняются. Рядом — `ProgramData\ClubDiskless\image.json` с версией
образа; помощник сообщает её серверу.

Образ **обязан** быть генерализован (`sysprep /generalize /oobe`): иначе у всех ПК один MachineGUID, и античит свяжет
машины. WinPE читает в залитом реестре `SOFTWARE\Microsoft\Windows\CurrentVersion\Setup\State` → `ImageState`:
генерализованным считается только `IMAGE_STATE_GENERALIZE_RESEAL_TO_OOBE`. Другое значение (у Windows без sysprep —
обычно `IMAGE_STATE_COMPLETE`) или нет значения — отказ `notGeneralized`, образ помечается в панели, и следующие
запросы перезаливки им отказывают сразу (`notGeneralized` до стирания диска). Задания, созданные раньше пометки (тем
же образом заливают несколько ПК), отказывают в WinPE ещё до плана: `notGeneralized` на `POST /deploy/v1/start`, диск
не тронут, задание можно отменить. Куст SOFTWARE не загрузился (`reg load`
с ошибкой) — тоже отказ, но образ не помечается: разовый сбой не должен клеймить хороший образ (на экране WinPE
`ImageState=unreadable`, в сообщении задания `unknown`). Если WinPE ничего не сообщил — так же.
`SYSTEM\Setup\Status\SysprepStatus\GeneralizationState` — только для диагностики: оба значения видны на экране WinPE,
в сообщении задания и в логе сервера. WinPE сообщает и то, загрузился ли куст SYSTEM (`systemHiveLoaded`): в
сообщении задания `GeneralizationState=none` — куст прочитан, значения нет; `unknown` — куст не прочитан (на экране
`unreadable`) или WinPE ничего не сообщил.
[ГИПОТЕЗА: в `install.wim` Microsoft — `IMAGE_STATE_GENERALIZE_RESEAL_TO_OOBE`; проверить первой заливкой образа Microsoft.]

**Исключение — эталонный ПК** (гибрид из эталона бездиска): на него заливается копия эталона без sysprep, а
генерализованный образ потом снимается с него самого. Запрос перезаливки через API с `allowNotGeneralized: true`
(в панели кнопки нет, `docs/panel-api.md`). Разрешение хранится в задании и действует только на него: WinPE
получает его в плане (`POST /deploy/v1/start`), значения показывает и сообщает, но не отказывает; сервер не
превращает `generalized: false` в `notGeneralized`. Следующая перезаливка без флага снова требует sysprep: после
первой же такой заливки образ помечен «не генерализован», и запрос без флага отказывает сразу. Такой образ на другие
ПК не заливать: у всех будет один MachineGUID. Поэтому его импортируют, но не публикуют: запрос с `image: "<метка>"`
берёт любую готовую версию, а опубликованная стала бы версией по умолчанию. Сервер это проверяет сам: импорт сразу
помечает версию «не генерализован», если описание образа в WIM содержит «not generalized» (так подписывает эталон
`make-hybrid-ref.py`; версии, импортированные раньше, сервер узнаёт по тому же описанию) или в запросе импорта
`notGeneralized: true` (только API), — и публикация такой версии (`generalized: false`, в том числе найденной первой
заливкой) — отказ `imageNotGeneralized`; откат на такую версию — тот же отказ. Без пометки сервер до первой заливки не знает, что образ без sysprep, и
опубликованный образ стёр бы диск первого же ПК до отказа на шаге identity.

## Установка на сервере (от root)

Каталоги и настройки сервера клуба:

```json
"Imaging": {
  "Enabled": true,
  "Root": "/srv/club/images",
  "PxeRoot": "/srv/club/pxe",
  "PublicBaseUrl": "http://192.168.77.1:5080",
  "BcdbootAddLast": false
}
```

`PublicBaseUrl` — адрес сервера для ПК по **HTTP** (iPXE и WinPE): сервер должен слушать этот адрес в сети клуба.
`Root/incoming/` — сюда кладётся `install.wim` (scp или SMB); `Root` может быть смонтированным датасетом TrueNAS.

TFTP и подписанная цепочка (iPXE v2.0.0 и wimboot v2.9.0 из официальных релизов, sha256 закреплены в скрипте):

```bash
apt install -y tftpd-hpa
sudo scripts/pxe/install-boot-files.sh
```

Скрипт кладёт в `/srv/tftp` `ipxe-shim.efi`, `ipxe.efi` (подписанный, из `x86_64-sb`) и `undionly.kpxe`, в
`/srv/club/pxe` — `wimboot` (каталоги меняются `TFTP_ROOT`/`PXE_ROOT`; `Imaging:TftpRoot` должен совпадать).
Пакет Ubuntu `ipxe` не нужен: его `ipxe.efi` не подписан.

**WinPE** — один на оба случая: перезаливка по PXE (файлы ниже) и флешка для снятия образа с эталона («Снятие
гибридного образа» ниже). Собирается на бездисковом месте (PC-01/PC-02), не на эталоне PC-11: ADK остался бы в образе.
Место сбрасывается при перезагрузке, поэтому ADK ставится и WinPE собирается в одном сеансе, без перезагрузки.

Основной путь — скрипты `scripts/winpe/` с флешки, на которой они лежат рядом: `adk-install.cmd`,
`winpe-run-as-admin.cmd`, `winpe-finish-run-as-admin.cmd`, `build-winpe.cmd`, `capture-hybrid.cmd`,
`capture-hybrid.ps1`. Шаги ниже запускаются правой кнопкой → «Запуск от имени администратора»; сбой — `FAIL` и
пауза (окно сфотографировать).

1. `adk-install.cmd` — скачивает с сервера `adksetup.exe` и `adkwinpesetup.exe` (sha256 сверяется) и запускает их по
   очереди. Лицензию принимает человек; в обоих — «Install the … to this computer» (не Download), в ADK отмечен только
   «Deployment Tools». Сам комплект установщики качают у Microsoft — месту нужен интернет. Проверка: `DandISetEnv.bat`,
   `copype.cmd`, `WinPE-PowerShell.cab`; свободно на системном диске меньше 15 ГБ — предупреждение.
2. `winpe-run-as-admin.cmd` — скачивает `winpe-drv-e1d.zip` (Intel I219-V e1d 12.19.2.65, sha256 сверяется) и
   распаковывает в `%SystemDrive%\ClubWinPE-drv`, показывает съёмные тома и спрашивает букву пустой флешки для снятия
   образа (8 ГБ и больше; Enter — без флешки; букву флешки со скриптами не принимает), вызывает
   `build-winpe.cmd /drivers %SystemDrive%\ClubWinPE-drv /usb <буква>:` (ниже) и копирует результат
   (`%SystemDrive%\ClubWinPE\out\pxe`) в `winpe-out` рядом с собой, в конце — sha256 `boot.wim`.
3. Запись флешки упала после форматирования (на флешке FAT32 с меткой `WINPE`) — в том же сеансе
   `winpe-finish-run-as-admin.cmd`: копирует собранный `%SystemDrive%\ClubWinPE\work\media` на единственный съёмный
   том с меткой `WINPE` (не на флешку со скриптами), проверяет `\EFI\Boot\bootx64.efi` и `boot.wim` (`fc /b`), кладёт
   в корень `capture-hybrid.*` и копирует `winpe-out`. Флешка не отформатировалась — сначала вручную
   `format E: /FS:FAT32 /Q /V:WINPE`.

Файлы для этих скриптов — в `<Imaging:PxeRoot>/tools/` (`/srv/club/pxe/tools/`), скрипты берут их по
`http://192.168.1.201:5080/pxe/v1/files/tools/<файл>`. SHA-256 закреплены в скриптах: другой файл — другая сумма в
скрипте.

| Файл | Что | SHA-256 |
|---|---|---|
| `adksetup.exe` | установщик Windows ADK (Microsoft) | `ac6a930fdb5c2980ba5fefe606d47edaafcf5f647b4337411500d158ea77300f` |
| `adkwinpesetup.exe` | установщик WinPE add-on (Microsoft) | `d4de67acc83de253ccc941dd0590808d83726bdd8ea768a374a7beaff7949d6a` |
| `winpe-drv-e1d.zip` | драйвер Intel I219-V e1d 12.19.2.65 для WinPE | `ffd2f77db63298b4f02bee617e3ec7307a7fc9e74b5f25632b857a4ba19de5dc` |

Вместо `winpe-run-as-admin.cmd` — вручную, командная строка от администратора (после `adk-install.cmd`; рядом с
`build-winpe.cmd` должны лежать `capture-hybrid.cmd` и `capture-hybrid.ps1`):

```
net use \\192.168.1.201\incoming /user:clubimg *
build-winpe.cmd /drivers \\192.168.1.201\incoming\winpe-fix\drv /usb E:
robocopy C:\ClubWinPE\out\pxe \\192.168.1.201\incoming\winpe-out /e
```

Что делает `build-winpe.cmd`:

- Окружение ADK скрипт открывает сам (`DandISetEnv.bat`). Работа и результат — на системном диске
  (`%SystemDrive%\ClubWinPE\work` и `…\out\pxe`): DISM не монтирует образ в сетевой папке. Остатки прошлого запуска
  (смонтированный образ, `work`) убираются; не убралось — `dism /Cleanup-Mountpoints`.
- `copype amd64`, пакеты WinPE-WMI, -NetFX, -Scripting, -PowerShell, -StorageWMI, -DismCmdlets (и их en-us).
- `/drivers <папка>` — все `.inf` из папки и подпапок вместе с их файлами — в `boot.wim`: папка копируется на
  локальный диск, затем `dism /Add-Driver /Recurse`, список на экране — `dism /Get-Drivers`. Сейчас это Intel I219-V:
  из пакета Intel только `PRO1000\Winx64\NDIS68` (e1d, служба `e1dexpress`, поколения 1–27); позже Realtek
  RTL8111/8125 — добавить подпапку и собрать заново. Без `/drivers` — предупреждение: у WinPE только встроенные
  драйверы, на I219-V сети нет, и заливка бесконечно повторяет `/deploy/v1/start`.
- `dism /Set-ScratchSpace:512` — рабочее место на RAM-диске X: 512 МБ вместо 32 по умолчанию.
- `boot\bootx64.efi` — загрузчик CA 2023 из `Windows\Boot\EFI_EX` WinPE, если он там есть (иначе сообщение `NOTE`).
- В конце — sha256 `sources\boot.wim`: сверить после копирования на сервер (`sha256sum`).
- `/usb E:` — тот же WinPE ещё и на флешку. **Раздел форматируется**, всё на нём пропадает: не та флешка, на которой
  носим файлы (букву, с которой запущен сам скрипт, он не принимает). До сборки скрипт проверяет, что E: — раздел на
  диске с шиной USB, не на диске работающей Windows и не больше 32 ГБ (больше `format` в FAT32 не форматирует —
  сделать раздел меньше в diskpart), показывает модель, размер и метку, запоминает диск и раздел (UniqueId, серийный
  номер и размер диска, смещение и размер раздела — в `%SystemDrive%\ClubWinPE\usb-stick.txt`, вне удаляемого `work`)
  и ждёт `YES`. После сборки — та же проверка и сверка с запомненным: под E: теперь другой диск или раздел (флешку
  подменили, буквы съехали) — отказ, ничего не форматируется. Затем `format E: /FS:FAT32 /Q /V:WINPE /X /Y`,
  `robocopy` содержимого `work\media` на флешку, проверка `\EFI\Boot\bootx64.efi`, сверка `boot.wim` с собранным
  (`fc /b`), в корень — `capture-hybrid.cmd` и `capture-hybrid.ps1`. Ни active-раздела, ни bootsect: все ПК клуба
  грузятся только по UEFI (CSM выключен), а UEFI сам находит `\EFI\Boot\bootx64.efi` на FAT32. `MakeWinPEMedia /UFD`
  не используется: на PC-01 (2026-10-23, Lexar 28,9 ГБ) он отформатировал флешку и упал на шаге `active`
  (`DiskPart errorlevel -2147024809`: GPT или съёмный диск). Скрипта заливки на флешке нет: WinPE с неё открывает
  обычную командную строку.

Любой сбой — `ERROR` и код выхода 1, смонтированный `boot.wim` отбрасывается. Сбой записи флешки `out\pxe` не
трогает: он уже собран, флешку дописывает `winpe-finish-run-as-admin.cmd`.

Первая сборка — PC-01, 2026-10-23: ADK 10.1.26100.9457, WinPE 10.0.26100.1, `boot.wim` sha256
`dfc6a31c48d34aef33e3b9e77952abfebc4d67e5c8972091a7bfeceb73669429`, `boot\bootx64.efi` — из `EFI_EX`, подпись
Windows UEFI CA 2023. Флешку тогда дописал `winpe-finish-run-as-admin.cmd`. [ГИПОТЕЗА: запись флешки самим
`build-winpe.cmd` (`format` + `robocopy`) ещё не запускалась — проверить следующей сборкой.]

На сервере (root): `winpe-out` с флешки — на сервер (например, в `incoming/winpe-out` по SMB или scp), оттуда в
`PxeRoot`, `winsetup/` не трогать. Подпапки `incoming` импорт образов не видит. `sha256sum` `boot.wim` должен
совпасть с тем, что скрипт показал в конце.

```bash
cd /srv/club/images/incoming/winpe-out && sha256sum sources/boot.wim
for f in boot/BCD boot/boot.sdi sources/boot.wim boot/bootx64.efi; do [ -f "$f" ] && install -D -m 644 "$f" "/srv/club/pxe/$f"; done
```

Итог в `PxeRoot`:

```
/srv/club/pxe/wimboot            ← install-boot-files.sh
/srv/club/pxe/boot/BCD
/srv/club/pxe/boot/boot.sdi
/srv/club/pxe/boot/bootx64.efi   ← загрузчик с подписью Windows UEFI CA 2023 (необязателен)
/srv/club/pxe/sources/boot.wim
```

Всё видно в панели: «Образы Windows» → «Файлы загрузки по сети» — есть ли файл, кем подписан, цела ли подпись,
версия.

Скрипт заливки, `winpeshl.ini` и `clubdeploy.json` (адрес сервера) в `boot.wim` не зашиваются — wimboot берёт их
с сервера при каждой загрузке, поэтому обновление сервера обновляет и заливку.

Kea: после включения образов заново скачать `kea-dhcp4.conf` на экране «Сеть» и установить (`docs/network.md`) —
в нём появятся классы `club-reimage-*`.

Прошивка каждого ПК: UEFI, сетевая загрузка IPv4 включена. Порядок загрузки — один из двух вариантов:

- **Сеть первой** — для перезаливки достаточно перезагрузить ПК. ПК без флага получает адрес без загрузчика и через
  несколько секунд грузится с диска. [ГИПОТЕЗА: задержка зависит от платы — замерить на стенде.] Задумано вместе с
  `Imaging:BcdbootAddLast: true` (env `Imaging__BcdbootAddLast=true`): WinPE вызывает `bcdboot … /f UEFI /addlast`,
  чтобы запись Windows Boot Manager встала в конец и сеть осталась первой. Защищает от опасения, что `bcdboot`
  ставит Windows Boot Manager первым: тогда после первой же заливки ПК грузится сразу с диска, и следующая
  перезаливка повиснет в «ждёт загрузки по сети». [ГИПОТЕЗА, не проверено: WinPE вызывает bcdboot с `/s`, а с `/s`,
  по описанию Microsoft, запись в NVRAM прошивки не создаётся — тогда ключ ничего не меняет, и порядок решает сама
  прошивка (часть прошивок сама ставит найденный Windows Boot Manager вперёд). После bcdboot WinPE выводит на экран
  `bcdedit /enum firmware` — только для диагностики, на заливку не влияет; на стенде записать порядок после заливки
  (пункт 3a «Проверки на стенде»).]
- **Диск первым** — ежедневная загрузка не ждёт DHCP; для перезаливки после «Перезалить» — разовое меню загрузки
  платы (F12 на Gigabyte) → UEFI IPv4. `Imaging:BcdbootAddLast` не нужен (по умолчанию выключен).

Настройка общая для всех ПК, поэтому порядок лучше выбрать один для всех: на ПК с диском первым `/addlast` тоже
уведёт Windows Boot Manager в конец, и первой окажется сеть. [ГИПОТЕЗА: проверить на стенде.]

## Образ: сборка и публикация

1. Золотой ПК: установка Windows → audit mode (Ctrl+Shift+F3 на OOBE) → весь софт, помощник бездиска
   (`docs/helper.md`) → `sysprep /generalize /oobe /shutdown /unattend:<ваш unattend>`.
2. Загрузиться с флешки WinPE (`build-winpe.cmd /usb`) и снять образ прямо в `incoming` на сервере:
   `capture-hybrid.cmd` («Снятие гибридного образа» ниже — проверка sysprep, временное имя, которое импорт не видит).
   Вручную: `dism /Capture-Image /ImageFile:<файл>.wim /CaptureDir:C:\ /Name:<метка> /Compress:max /ScratchDir:<не X:>`.
3. WIM — в `incoming/` на сервере (capture-hybrid.cmd кладёт сам). На экране «Образы Windows» — «Импортировать» с меткой
   версии (`win11-2609`) и индексом образа внутри WIM. Сервер переносит файл, читает состав WIM, считает sha256.
4. «Опубликовать»: версия становится текущей, прежняя текущая — откатной, более старая удаляется (когда её не
   использует ни одна незавершённая перезаливка). «Откатить» меняет текущую и откатную местами. Версию «без sysprep»
   (`generalized: false`) опубликовать нельзя (`imageNotGeneralized`, в панели кнопки нет), и откат на неё — тот же
   отказ.

Импорт переживает падение сервера на любом шаге (перенос через `.partial`, повтор с начала шага).

## Перезаливка

«Рабочие станции» → «Перезалить» (текущая или откатная версия) → перезагрузить ПК. Ход виден в строке машины:
ждёт загрузки по сети → разметка → скачивание (проценты) → проверка → распаковка → имя ПК → загрузчик → первая
загрузка Windows → перезалит. Сбой показывает этап и причину; ПК на экране WinPE ждёт Enter (без перезагрузок
по кругу). Сервер не перезагружает ПК сам.

Бездисковые ПК (`bootMode: diskless`) и ПК в режиме мастера не перезаливаются: их Windows — на сервере, а взведённое
задание перехватывает загрузку по сети раньше iSCSI, и WinPE стёр бы локальный диск. Запрос — отказ `disklessMachine`
(и в API, не только в панели); сначала режим `local` / выключить режим мастера. Обратно так же: пока перезаливка
взведена (в том числе упавшая — ПК остаётся в PXE), переключение в `diskless` и в мастера — отказ `reimageActive`;
сначала отменить или довести перезаливку. Обе стороны проверяют друг друга в одной транзакции под блокировкой строки
машины (`SELECT … FOR UPDATE`, затем отдельный запрос), поэтому одновременные запрос и переключение не проходят оба.
Последний рубеж — WinPE: если задание всё же взведено у бездискового ПК или мастера, `POST /deploy/v1/start` падает с
`disklessMachine` до плана, диск не тронут, задание можно отменить.

## Известные ограничения и открытые вопросы

- **Secure Boot** — подписанная цепочка сделана, но на железе не проверялась; shim подписан только CA 2011,
  поэтому ПК без стороннего CA Microsoft в db (часть ноутбуков и Secured-core) без изменения настроек платы не
  загрузятся по сети — сервер скажет об этом заранее.
- Образ скачивается по HTTP без авторизации: во время перезаливки его может скачать любой в сети клуба, подделав
  MAC. В образе — ключ клуба помощника (`helper.json`); с ним можно только зарегистрировать машину, которую потом
  одобряет администратор.
- USB-обёртка того же WIM, активация Windows (OEM/MAK/KMS), раздел восстановления — не сделаны.
- WinPE-часть проверена только в PowerShell 7 на Linux с заглушками команд Windows (`DeployScriptTests`):
  API, скачивание с докачкой, sha256, порядок шагов, сбой и повтор. Командлеты дисков, dism, bcdboot, wimboot и
  прошивки — только на стенде. Отличия PowerShell 5.1 WinPE от 7.x (например, `ConvertTo-Json` строк из
  `Get-Content`) эти тесты не ловят; без `PWSH` они пропускаются (Skip).

## Проверка на стенде

1. Собрать WinPE, положить файлы, включить `Imaging`, обновить конфиг Kea; `curl http://<сервер>/pxe/v1/boot.ipxe`.
2. ПК с Secure Boot off, сеть первой: без флага — грузится с диска (засечь задержку).
2a. ПК с Secure Boot **on**: перезаливка проходит (shim → iPXE → wimboot → WinPE); ПК с отключённым сторонним CA —
    в панели отказ `secureBootThirdPartyCa`; ПК с применённым отзывом PCA 2011 — грузится загрузчиком CA 2023.
3. «Перезалить» → перезагрузка → WinPE → заливка → Windows с именем места; в панели «перезалит».
3a. Порядок загрузки после заливки (к гипотезе про `/addlast`): сфотографировать вывод `bcdedit /enum firmware` на
    экране WinPE после bcdboot (не открылось хранилище — строка `(ignored)`, тогда только по Windows); в Windows от
    администратора `bcdedit /enum firmware` → `displayorder` у `{fwbootmgr}`; Boot Option #1 в BIOS. Сделать с
    `Imaging:BcdbootAddLast` false и true. При сети первой следующая перезаливка должна начинаться простой перезагрузкой.
4. Выдернуть сеть во время скачивания → докачка после возврата. Выключить ПК во время dism → после включения
   снова WinPE, заливка с нуля.
5. ПК с двумя дисками и флешкой — стёрт только системный; `diskChanged`/`systemDiskNotFound` при подмене диска.
6. Образ без sysprep → `notGeneralized`; `ImageState` и `GeneralizationState` в образе до/после sysprep (экран WinPE,
   сообщение задания). Эталонный ПК с `allowNotGeneralized: true` — заливка проходит с предупреждением.
7. FACEIT/Vanguard на перезалитом ПК; уникальность MachineGUID на двух ПК (`reg query HKLM\SOFTWARE\Microsoft\Cryptography /v MachineGuid`).
8. Q5: время заливки WIM 20+ ГБ по сети на 1 и 10 ПК одновременно.

## Эталонный WIM гибрида из версии бездиска (make-hybrid-ref.py)

Гибридный образ делается из опубликованного эталона бездиска через эталонный ПК (PC-11). Первый шаг — WIM этого
эталона без sysprep, исправленный для загрузки с локального SSD. Его снимает на сервере `scripts/server/make-hybrid-ref.py`
(clubadmin, sudo). Эталон и места не затрагиваются: скрипт работает с временным клоном снимка.

```bash
sudo apt install python3-hivex        # один раз; wimtools, ntfs-3g, open-iscsi, python3-websocket уже стоят
tmux                                  # снятие идёт долго, обрыв ssh не должен оставить его без присмотра
sudo python3 ~/scripts/server/make-hybrid-ref.py v2-2026-10-22    # → incoming/ref-v2-2026-10-22.wim (--label — другая метка)
sudo python3 ~/scripts/server/make-hybrid-ref.py --cleanup v2-2026-10-22   # только убрать остатки прерванного запуска
sudo python3 ~/scripts/server/test-wof.py -v   # тесты шага WOF (без TrueNAS; на VM — с компрессорами libwim)
```

`--cleanup` убирает временное в TrueNAS и на VM и недописанный `incoming/<метка>.wim.partial` (версия или `--label` —
как у прерванного запуска). Без версии и `--label` удаляются все `incoming/*.wim.partial`: их пишет только этот скрипт
(импорт сервера идёт через `images/<метка>/`, `capture-hybrid.ps1` — через `incoming\capture-tmp`).

Что делает (TrueNAS — по JSON-RPC, как сервер, с ключом из `club-server.env`; ключ не выводится):

1. Временное в TrueNAS: клон `ssd/club/diskless/hybrid-ref-tmp` снимка `@img-<версия>`, группа инициаторов
   `clubsrv hybrid-ref-tmp` только с IQN этой VM (`/etc/iscsi/initiatorname.iscsi`), экстент и таргет
   `hybrid-ref-tmp` без CHAP, LUN 0. Видимость таргета проверяется SendTargets с VM, при необходимости — повторный
   reload, как при публикации. Экстент на запись намеренно: read-only устройство в TrueNAS 25.10 срывает reload SCST.
   На VM диск сразу переводится в read-only (`blockdev --setro`).
2. Вход по iSCSI: запись узла только для этого таргета; discovery без записи в базу узлов, чтобы не задеть том
   образов. Раздел Windows — NTFS с `Windows\System32\config\SYSTEM` (проба ntfs-3g только на чтение). Его куст SYSTEM
   проверяется сразу, до снятия: чистый (см. п. 5), в наборе `Select\Current` есть `storahci`, `stornvme`, `MSiSCSI`.
3. Файлы со «сжатием системы» (WOF, `compact /CompactOS`: точка повторной обработки 0x80000017, провайдер FILE —
   `servicing\Packages`, `CatRoot`, `WinSxS\Catalogs`, Defender, `WindowsApps`, Chrome…) становятся обычными файлами
   **на клоне**. Снятие в режиме NTFS-3G хранит их как есть (точка + поток `WofCompressedData`, данных нет), и DISM на
   таком WIM падает на 1 % с «Error: 1 Incorrect function» (PC-11, 2026-10-23). Только на этот шаг диск делается
   доступным на запись (`blockdev --setrw`; клон одноразовый, эталон и его снимок не трогаются), раздел монтируется
   ntfs-3g на запись (`norecover,noatime,streams_interface=windows`; тайм-ауты FUSE через `-o` ntfs-3g не передаёт,
   поэтому первый `lstat` файла после снятия точки может дать EIO — он повторяется). Обход всего тома: у каждой
   записи читается точка повторной обработки; провайдер WIM (WIMBoot) или непонятные данные — отказ до первого
   изменения. Каждый файл (жёсткие ссылки — один раз): точка снимается, поток разжимается libwim через ctypes
   (XPRESS4K/8K/16K, LZX — форматы WIM), пишется в сам файл, поток удаляется; атрибуты и время (создание, запись,
   доступ) возвращаются, дескриптор безопасности не трогается и сверяется. Затем диск снова read-only, свежий
   монтаж только на чтение: ни одной WOF, размеры и sha256 совпадают. В лог — sha256 нескольких файлов (по одному на
   формат) для сверки с `Get-FileHash` на месте с этой версией. Любой сбой — клон уничтожается обычной очисткой.
4. `wimlib-imagex capture` прямо с раздела (режим NTFS-3G: ACL, потоки, точки повторной обработки, короткие имена),
   LZX, таблица целостности. Исключения — как у DISM (pagefile, hiberfil, System Volume Information…) и файлы помощника
   `credentials.bin*`, `assignment.json*`. Затем `wimlib-imagex dir --detailed`: в WIM нет ни тега 0x80000017, ни
   потока `WofCompressedData` — иначе отказ. Сразу после — выход из iSCSI и удаление всего временного в TrueNAS. Не
   удалось (например, сорвался reload SCST и zvol занят) — только предупреждение: WIM доделывается, удаление
   повторяется в конце.
5. Реестр внутри WIM (куст SYSTEM, набор из `Select\Current`, hivex):
   - `storahci`, `stornvme`: Start=0, подключ `StartOverride` удалён (иначе 0x7B на AHCI/NVMe);
   - службы, которым подготовка бездиска поставила загрузку при старте (`iScsiPrt`, `e1dexpress`, `rt640x64` и др. —
     `install.cmd` из `extract-winsetup.sh`, `prepare-golden.ps1`; плюс драйверы всех сетевых карт PCI, которые видел
     эталон): Start 0 → 3, `BootFlags` удалён;
   - `MSiSCSI`: автоматически (её ждёт помощник для G:).

   Куст с неприменённым журналом (`SYSTEM.LOG1/LOG2`) — отказ: снимок сделан не после чистого выключения.
6. `wimlib-imagex verify`, `.wim.partial` → `.wim`, размер и sha256. Лог — `/var/log/make-hybrid-ref.log`.

Сбой, Ctrl+C, обрыв ssh — та же очистка (всё ищется по имени), `.wim.partial` удаляется; остаётся только проверенный,
если имя `<метка>.wim` за это время заняли (переименовать его вручную в другую метку). Повторный запуск сначала
убирает остатки прошлого. Не удалось убрать (TrueNAS недоступен) — код выхода 1 и `--cleanup` позже; готовый `.wim`
при этом не трогается.

Дальше: «Образы Windows» → «Импортировать» `ref-v2-2026-10-22.wim`, метка `ref-v2-2026-10-22`, индекс 1.
**Не публиковать**: образ не генерализован. Сервер и не даст: по описанию WIM («not generalized») импорт помечает
версию «без sysprep», публикация — отказ `imageNotGeneralized`. Залить им только эталонный ПК — запрос с
`image: "<метка>"` и `allowNotGeneralized: true` («Личность машины» выше).

Проверка разжатия без TrueNAS, на одном образце (root не нужен): `python3 make-hybrid-ref.py --selftest-wof <точка>
<поток> <размер> [--out файл]` печатает формат, число блоков и sha256. Образец берётся с любого NTFS с такими файлами
без монтирования: `ntfscat -a 0xC0 <раздел> <путь> | xxd -p` (точка), `ntfscat -a 0x80 -n WofCompressedData <раздел>
<путь> > поток`, `ntfscat <раздел> <путь> | wc -c` (размер).

[ГИПОТЕЗЫ — проверить первым запуском: время снятия (порядок 30–60 мин) и нагрузка на пул ssd, с которого работают
места, — запускать, когда клуб не загружен; размер WIM. Шаг WOF: время (два обхода тома и запись нескольких ГБ),
сколько места клон займёт в пуле (разжатые данные пишутся в него), sha256 из лога = `Get-FileHash` на месте;
после заливки PC-11 — `sfc /verifyonly`. Сжатие на PC-11 при желании вернуть: `compact /CompactOS:always`.
Заменённый `SYSTEM` хранится в WIM без своего дескриптора безопасности: DISM даст ему ACL, унаследованный от `config`
(на PC-11 сверить `icacls C:\Windows\System32\config\SYSTEM` с соседними кустами).]

## Снятие гибридного образа с эталонного ПК (capture-hybrid.cmd)

После `scripts/golden/seal-hybrid.ps1` эталонный ПК (PC-11) выключен sysprep'ом (`/generalize /oobe /shutdown`). Эту
Windows **не загружать**: первая же загрузка проходит specialize и OOBE, и эталон придётся печатать заново.

1. Флешка `WINPE` из `build-winpe.cmd /usb` (`winpe-run-as-admin.cmd`) → при включении F12 → «UEFI: <флешка>» (не
   Windows Boot Manager; только UEFI — загрузочного сектора для CSM на флешке нет). Secure Boot выключать не нужно:
   загрузчик WinPE подписан Microsoft. [ГИПОТЕЗА: на Z490M F24a PCA 2011 не отозван — проверить первой загрузкой.]
2. В командной строке WinPE найти флешку (`for %d in (C D E F G H) do @if exist %d:\capture-hybrid.cmd echo %d:`) и
   запустить, например, `D:\capture-hybrid.cmd`. Можно сразу с параметрами: `-Drive C -Label h1-2026-10-24`.

Что делает `capture-hybrid.ps1` (тексты на экране — английские):

1. Отказ, если это не WinPE. Раздел Windows — буква с `Windows\System32\config\SYSTEM`, кроме X: (сам WinPE). Нет —
   подсказка (diskpart, `assign`); несколько — список (метка, размер, ImageState) и выбор буквы, Enter — отмена.
2. Генерализация — та же проверка, что у WinPE при заливке («Личность машины»): куст SOFTWARE,
   `Microsoft\Windows\CurrentVersion\Setup\State` → `ImageState` должен быть `IMAGE_STATE_GENERALIZE_RESEAL_TO_OOBE`.
   Другое значение или его нет — отказ; куст не загрузился или не выгрузился — ошибка (у `reg` проверяется код выхода).
   `GeneralizationState` из SYSTEM — только для записи: оба значения на экране и в журнале на флешке (к гипотезе в
   «Личности машины»). Остались `credentials.bin*`/`assignment.json*` помощника — список и удаление только после `Y`
   (их убирает seal-hybrid.ps1; в образе они достались бы всем гибридам).
3. Ждёт сеть до 2 мин (порт 445 сервера). Не дождался — `ipconfig /all` и отказ; нет адреса IPv4 — в WinPE нет драйвера
   сетевой карты, собрать с `/drivers`.
4. `net use \\192.168.1.201\incoming * /user:clubimg /persistent:no`: пароль clubimg вводит человек (не виден, нигде
   не сохраняется), три попытки. В конце соединение удаляется.
5. Метка — по правилу импорта (`^[a-z0-9][a-z0-9._-]{0,39}$`, `ImageLibrary.cs`), например `h1-2026-10-24`. Уже есть
   `incoming\<метка>.wim` — спросит другую. Свободного места в `incoming` меньше, чем занято на разделе Windows, —
   вопрос (WIM со сжатием max меньше занятого).
6. `dism /Capture-Image /ImageFile:\\192.168.1.201\incoming\capture-tmp\<метка>.wim /CaptureDir:<W>:\ /Name:<метка>
   /Compress:max /CheckIntegrity /ScratchDir:<флешка>\capture-scratch` (другое место — `-ScratchDir`). Scratch — на
   флешке: X: — RAM-диск на 512 МБ, а на снимаемый раздел писать нельзя. Подпапку `capture-tmp` импорт не видит (он
   смотрит только `*.wim`/`*.esd` в корне `incoming`), так что недописанный образ в панели не появится. Сбой dism —
   недописанный файл удаляется.
7. `dism /Get-WimInfo` по готовому файлу, затем перенос в `incoming\<метка>.wim` (переименование на сервере,
   мгновенное) и размер на экране. Сбой после снятия — файл остаётся в `capture-tmp`, перенести вручную.

Журналы — на флешке: `capture-hybrid.log` (экран) и `capture-hybrid-<метка>-dism.log`.
