# Проверка самообновления помощника на PC-22 и PC-23

Порядок проверки самообновления помощника 1.8.0 в клубе. Спецификация:
`docs/superpowers/specs/2026-11-06-helper-self-update-design.md`, п. 1 (критерий готовности) и п. 7 (проверка); план —
`docs/superpowers/plans/2026-11-06-helper-self-update.md`, задачи 11–12; как устроено — `docs/helper.md`, раздел
«Самообновление (1.8.0)».

Каждый шаг — только после ОК владельца. Пока идёт проверка:

- на PC-22 и PC-23 не ставить и не удалять шелл: набор шелла в `tools` ещё со старыми проверками, на ПК с 1.8.0 они
  дают FAIL (`docs/helper.md`, «Обновление до 1.8.0 в клубе», п. 4);
- на обоих ПК нет игроков: при выданных сохранениях замена ждёт конца сеанса («ждёт: сеанс»);
- по шагам ниже PC-22 ломается, PC-23 ждёт в очереди.

## Команды на ПК

Вход `Club` (Shift при входе — мимо киоска), PowerShell от администратора. Окно не закрывать до конца шага: в нём
запомнено время начала шага (`$since`).

**Начало шага** — до «Запустить» в панели:

```powershell
$since = Get-Date
```

**Снимок ПК** — служба, версия и сборка помощника, файлы обеих папок, состояние замены, сессии iSCSI:

```powershell
$p = Join-Path $env:ProgramFiles 'ClubDiskless'
$d = Join-Path $env:ProgramData 'ClubDiskless'
Get-Service ClubDisklessHelper | Format-Table Status, Name, DisplayName -AutoSize
Get-Content (Join-Path $d 'helper-build.json')
(Get-FileHash -Algorithm SHA256 -LiteralPath (Join-Path $p 'ClubDisklessHelper.exe')).Hash.ToLowerInvariant()
Get-ChildItem -LiteralPath $p, $d | Format-Table FullName, Length, LastWriteTime -AutoSize
Get-Content (Join-Path $d 'update.json') -ErrorAction SilentlyContinue
Get-Content (Join-Path $d 'update-failed.json') -ErrorAction SilentlyContinue
Get-IscsiSession | Format-Table TargetNodeAddress, SessionIdentifier, IsConnected -AutoSize
```

Версию помощника показывает `helper-build.json` (`{"v":1,"version":"1.8.0","build":"05a73a8f…"}`), если `build` в нём
равен SHA256 exe из второй строки. Версия файла exe (свойства файла) о помощнике ничего не говорит: exe собирается на
Linux, там версия среды .NET (`10.0.x`). В панели (вкладка «Рабочие станции») то же видно в столбце «Помощник»:
`версия · 8 символов SHA256`, полный SHA256 — в подсказке.

**События с начала шага** — журнал «Система» (7031/7034: служба помощника завершилась нечисто, Windows её
перезапускает) и строки самообновления в журнале «Приложение» (источник `ClubDisklessHelper`):

```powershell
Get-WinEvent -FilterHashtable @{ LogName = 'System'; ProviderName = 'Service Control Manager'; Id = 7031, 7034; StartTime = $since } -ErrorAction SilentlyContinue |
    Where-Object { $_.Properties[0].Value -eq 'Club diskless helper' } |
    Sort-Object TimeCreated | Format-List TimeCreated, Id, Message
Get-WinEvent -FilterHashtable @{ LogName = 'Application'; ProviderName = 'ClubDisklessHelper'; StartTime = $since } -ErrorAction SilentlyContinue |
    Where-Object { $_.Message -match 'update' } |
    Sort-Object TimeCreated | Format-List TimeCreated, LevelDisplayName, Message
```

**Перезапуск службы при сбое:**

```powershell
sc.exe qfailure ClubDisklessHelper
```

Должно быть: `RESET_PERIOD (in seconds) : 86400`, `RESTART -- Delay = 5000 milliseconds` дважды и
`RESTART -- Delay = 30000 milliseconds`.

**Сколько ждать.** Windows считает сбои службы и обнуляет счётчик, только когда сутки не было ни одного сбоя
(`RESET_PERIOD` 86400): после первого и второго сбоя служба перезапускается через 5 с, после третьего и дальше — через
30 с. Каждая замена — тоже сбой для Windows (помощник завершает свой процесс), поэтому на PC-22 каждая следующая проба
идёт дольше: после шага 2 у него уже один сбой, к шагу 4 все перезапуски — по 30 с. Откат — это пять перезапусков
подряд: замена, три падения новой сборки, ветка отката.

## Сервер

На ВМ сервера клуба (владелец):

```bash
sudo grep '^HelperUpdates__' /etc/club-server/club-server.env
ls -l /srv/club/pxe/tools/ClubDisklessHelper-1.8.*.exe
sha256sum /srv/club/pxe/tools/ClubDisklessHelper-1.8.*.exe
sudo journalctl -u club-server --since '2026-11-07 00:00' --no-pager | grep 'Helper update'
```

Последняя строка — журнал сервера по очереди: запуск, отказы, смена состояния каждого поручения, «Продолжить».

## Шаг 0. Сервер с `HelperUpdates__MaxActive=1`

Сделано 2026-11-07 00:06: сервер `f9124e6` выкачен, в `/etc/club-server/club-server.env` — строка
`HelperUpdates__MaxActive=1`, затем `sudo systemctl restart club-server`. С одним активным поручением второй ПК стоит в

1.8.92 с SHA256 из таблицы выше (сборки старше 1.8.0 — с пометкой «только вручную»). В очереди — «Активно: 0/1»
(вторая цифра — `MaxActive`).

Что прислать: снимок карточки; вывод `grep` и `sha256sum` из раздела «Сервер».

## Шаг 2. 1.8.1 кнопкой на «22, 23»

1. На обоих ПК — «Начало шага» и «Снимок ПК» (это «до»: запомнить `SessionIdentifier` сессий iSCSI G: и H:).
2. Панель → «Обновление помощника»: «Сборка» — `1.8.1 · e332fb00`, «Места» — `22, 23` → «Запустить». Ответ:
   «Сборка 1.8.1: в очереди ПК — 2 (22-23).» В очереди — две строки «в очереди», «Активно: 0/1», «В очереди: 2».
3. Дальше панель сама (раз в несколько секунд). Активным становится ПК, который первым отчитался (отчёт — раз в 30 с);
   у него по очереди:

   | Статус | Что значит |
   |---|---|
   | «назначено» | поручение выдано, отчёта о нём ещё нет («Активно: 1/1», «В очереди: 1») |
   | «скачивает» | `.new` скачивается в фоне, отчёты идут |
   | «перезапуск» | `.old`/`.new` поменялись местами, помощник завершил процесс, Windows через 5–30 с запускает новую сборку |
   | «проверка» | новая сборка работает и отчитывается; в столбце «Помощник» уже `1.8.1 · e332fb00` |
   | «готово» | 10 минут без падений и не меньше 5 принятых отчётов — `confirmed` |

   Так было на PC-22 2026-11-07: в очереди 00:19:27, назначено 00:19:42, скачивает 00:20:28, перезапуск 00:20:59,
   проверка 00:21:14 (новая сборка отчиталась через ~15 с после перезапуска), G: всё время подключён. «Готово» — не
   раньше чем через 10 минут после «проверка». Потом при своём отчёте активным становится второй ПК, у него всё то
   же. На оба — около 25 минут.
4. Во время «проверка» (на этом ПК): в «Снимке ПК» — `ClubDisklessHelper.exe` (1.8.1, SHA256 `e332fb00…`) и
   `ClubDisklessHelper.exe.old` (1.8.0), `update.json` с `"phase":"swapped"`, `helper-build.json` с `"version":"1.8.1"`.
5. После «готово» на обоих (это «после»): в «Снимке ПК» — exe 1.8.1, `.old`, `.new`, `update.json` нет;
   `helper-build.json` — 1.8.1, `build` = `e332fb00f7da03758727786a72847c46d5511b6cf0be9d354377dee94d659f8a`; сессии
   iSCSI G: и H: — те же `SessionIdentifier`, что «до», `IsConnected` = True. В очереди — «Готово за сутки: 2».
6. «События с начала шага»: в «Системе» — одно событие 7031 по `Club diskless helper` на ПК (замена). В «Приложении»
   по порядку: `offered by the server; downloading in the background`, `downloaded … SHA256 … verified`,
   `the PC is free; applying goes with the next status report`, `exe replaced with build 1.8.1 …`,
   `new build 1.8.1 (…) start 1 of 3; confirming`, `confirmed after …`,
   `the server accepted confirmed; update.json and the previous build … (.old) removed`.

Что прислать: «Снимок ПК» до и после с обоих ПК; «События с начала шага» с обоих; время каждой смены статуса в панели
(или снимки очереди); строки `Helper update` из журнала сервера.

## Шаг 3. 1.8.90 — падение после старта

Поручение на PC-22 запускается отдельно и раньше, чтобы ломался именно PC-22 (при «22, 23» одним запуском активным
стал бы тот, кто первым отчитается).

1. На обоих ПК — «Начало шага» и «Снимок ПК».
2. «Сборка» — `1.8.90 · aa03d6a4`, «Места» — `22` → «Запустить». Когда у PC-22 «назначено» или «скачивает» — та же
   сборка, «Места» — `23` → «Запустить». У PC-23 — «в очереди».
3. PC-22: «скачивает» → «перезапуск» → (может мелькнуть «проверка») → через 2–4 минуты «ошибка: startFailed»; в
   подсказке — «Новая сборка падала при запуске — помощник вернул прежнюю.» и текст помощника. В столбце «Помощник»
   — снова `1.8.1 · e332fb00`.
4. Очередь — на паузе: надпись «Очередь на паузе после ошибки…», кнопка «Продолжить», у PC-23 — «на паузе»;
   «На паузе: 1», «Ошибки за сутки: 1». PC-23 ничего не скачивал.
5. На PC-22 «События с начала шага»: в «Системе» — пять 7031 (замена, три падения 1.8.90, ветка отката); в
   «Приложении» — строки стража `start 1 of 3`, `start 2 of 3`, `start 3 of 3`,
   `did not start cleanly 3 times; rolled back to e332fb00 (exe -> .failed, .old -> exe)`, затем прежней сборки
   `failed: startFailed: …; reported until the server closes it` и
   `closed by the server (…); failure no longer reported`. Рядом могут быть события `.NET Runtime` и
   `Application Error` с `CLUB_TEST_FAULT_CRASH` — это и есть пробное падение.
6. На PC-22 «Снимок ПК»: служба Running, exe — 1.8.1 (`e332fb00…`), `.old` нет; `ClubDisklessHelper.exe.failed`
   (1.8.90) может остаться до следующего запуска службы; `update.json` нет (стёрт, когда сервер перестал присылать
   поручение); в `update-failed.json` — это поручение с `startFailed`. Сессии iSCSI — как в начале шага.
7. Отмена: в строке PC-23 «Отменить» → «Отменить обновление помощника на ПК 23 до 1.8.90?…» → «Отменить»; у PC-23 —
   «отменено». Пауза очереди — это поручения «на паузе»: других нет, поэтому надпись о паузе и кнопка «Продолжить»
   пропадают сами. «Продолжить» до отмены не нажимать: PC-23 вернулся бы в очередь и получил пробную сборку. PC-23
   по-прежнему `1.8.1 · e332fb00`, в его «Снимке ПК» нет `.new` и `update.json`.

Что прислать: время «перезапуск» и «ошибка» у PC-22; снимок очереди на паузе; с PC-22 — «События с начала шага» и
«Снимок ПК»; с PC-23 — «Снимок ПК» после отмены.

## Шаг 4. 1.8.91 — исключение в фоновой службе

Как шаг 3, сборка `1.8.91 · 75886a19`: сначала `22`, затем `23`.

- PC-22: после «перезапуск» в каждом запуске новая сборка успевает отправить один отчёт («проверка»), затем
  исключение `CLUB_TEST_FAULT_THROW`, хост останавливается, помощник завершает процесс — для Windows это сбой, как
  падение. Все перезапуски теперь по 30 с: «ошибка: startFailed» — через 3–4 минуты после «перезапуск». Затем снова
  `1.8.1 · e332fb00`.
- Очередь на паузе, у PC-23 — «на паузе»; журналы и файлы — как в шаге 3 (в тексте ошибки — `CLUB_TEST_FAULT_THROW`).
- У PC-23 «Отменить» (как в шаге 3, п. 7: пауза пропадает сама, «Продолжить» не нажимать).

Главное в этом шаге: исключение внутри службы не должно оставить службу просто остановленной. Если у PC-22 служба
`Stopped` и «ошибка» в панели не появилась — проверка не прошла.

Что прислать: то же, что в шаге 3.
